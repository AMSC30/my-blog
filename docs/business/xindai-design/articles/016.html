# 授信与额度管理

公众号：侃西东　·　发布日期：2026-09-28　·　微信原文open in new window

六、授信与额度管理

图2-29授信与额度全生命周期管理流程

在讲放款时我提过，一笔授信合同下可以多次提款，每次提款生成一笔借据。这套"先授信、后支用"的机制，背后是信贷系统里一个设计含量很高的领域，叫额度管理。额度管理解决的是"银行愿意借给这个客户多少钱、这些钱怎么被占用和释放"的问题。它看起来只是几个字段（总额度、已用、可用），但真正做起来，是信贷系统里最容易出账务差错的地方之一。

# （一）统一授信：把散落的额度收拢成体系

图2-30统一授信前后对比：从散落额度到体系化管控

早期银行做信贷，往往是"一笔业务一个额度"，客户在这个产品下贷了一笔款，就占用这个产品的额度，产品之间互不相通。客户在银行的总敞口到底多大，没有人说得清。这正是额度管理要解决的第一件事：统一授信。

统一授信，是把客户在机构内的全部授信敞口纳入一个统一的额度体系进行管理。客户先获得一个总的授信额度，这个额度可以在不同产品、不同机构之间拆分使用。机构类型包括贷款经营机构、主办机构、贷款核算机构、合作方机构等，产品也分信贷基础产品、可售产品、组合产品，这就决定了统一授信必须支持跨机构、跨产品的额度体系。一个集团客户在总行获得统一授信，再由各分支行在额度内分别发放贷款，额度要能按机构、按产品拆分管理。

统一授信的价值，在风控上体现得最直接。没有统一授信，客户可以在多个产品线重复借款而不被发现，实际敞口远超审批时看到的数字；有了统一授信，客户的总敞口一目了然，审批时能看到这个客户已经用了多少额度、还剩多少空间。这也是监管要求的"授信集中度管理"的基础。我在国有大行做集团客户统一授信时，最大的难点就是跨法人、跨系统的额度归集。不同分行、不同系统的授信数据要汇总到一个口径，数据质量稍有瑕疵，额度就会对不上。

集团授信的复杂度不在批总盘子，而在批完之后怎么切：按法人主体切到各家子公司、按产品切到流贷/固贷/票据，总敞口不能超集团核定额度；做对公授信必须把实控人个人、关联企业的负债和担保一并纳入统一口径，这是比看财报更重要的风控点。

# （二）额度体系：基础额度、产品额度与共享额度

图2-31三层额度体系：基础额度·产品额度·共享额度

在信贷系统的数据场景里，额度不是一张简单的大表，而是一套有层次的体系。从授信的处理流程看，客户先通过授信审批获得额度，额度开户后进入可用状态，后续在额度内支用。这个"额度开户"的动作在系统里对应一笔额度记录，它是额度管理的最小单位。

额度层次这个问题的答案，可以从两个维度看。一个是"产品维度"：基础产品定义额度的属性模板（额度上限、有效期、占用规则），可售产品在模板上限定具体取值；客户获得的是一个具体产品下的可售额度。另一个是"归属维度"：额度可以挂在客户名下，也可以挂在集团、项目、合作方名下。共享额度是额度体系里最考验设计的概念。多个客户共享一个额度（比如夫妻共同申请、集团成员共享），或一个额度被多个产品共享（比如一个综合授信额度同时支持流动资金贷款和票据承兑）。共享额度要解决的，是"谁用了多少"的分配问题：共享额度被一方占用后，其他方可用额度同步减少，释放时也要同步回补。

支用环节里有一项"额度产品控制"，说明支用时系统要按额度产品控制规则校验：支用金额不能超过剩余可用额度，支用期限不能超过额度有效期，支用利率要落在额度定价范围内。这套控制规则，就是额度状态机和支用动作之间的约束接口。

# （三）额度状态机：冻结、解冻与调额

图2-32额度状态流转：冻结·解冻·调额·失效

额度从开户到失效，有自己的生命周期，也就是我在第五节提到的额度状态机。额度的主要状态包括：生效、可用、冻结、失效。生效是额度开户后正式生效；可用是额度当前可被支用；冻结是额度暂时不可用（比如客户出现风险信号、额度被司法冻结）；失效是额度到期或永久不可用。

线上信贷的额度不是批完就固定的，系统会根据客户还款记录、征信更新、多头借贷变化实时动态调整：风险上升就自动降额冻结，还款表现好就自动提额，把新增风险挡在放款前。

额度状态机的系统实现，要小心并发这个老问题。额度是典型的"高并发热点数据"：多个支用请求同时到达，都要扣减同一个额度的可用余额，如果扣减操作不加控制，就会出现"两个请求都以为额度够用，都放款成功，结果超额支用"的事故。解决方法是把额度扣减做成原子操作：用数据库的乐观锁或悲观锁保证扣减的原子性，用额度流水记录每一笔占用和释放，做到"先校验、后扣减、扣减即记账"。我在做额度系统时有一条铁律：额度余额永远不要靠字段的最终值反推，而要靠占用流水累加，因为只有流水才能解释余额为什么是这个数。

# （四）额度与借据的关系：占用与释放

图2-33额度与借据：占用与释放的联动关系

额度管理最核心的机制，是额度与借据之间的占用与释放。一笔支用（借据）生成时，要从额度上占用相应金额；借据结清（或部分还款）时，要把相应金额释放回额度。这个"占用—释放"的循环，就是额度系统的主线。

放到对公和产业金融场景下，循环逻辑又不一样：对公的固定资产贷款、项目贷款基本都是不循环的，钱按项目进度放完就结束，还进去也不恢复；只有流动资金贷款会做循环额度，企业在一年的额度有效期内随借随还，到期要重新审批授信，不像零售额度可以用好几年。产业金融的额度基本都是"单笔对应单笔资产"的，比如一笔应收账款质押融资，这笔应收款收回了，对应的额度就释放，下一笔新的应收账款进来，再占对应的额度，不存在零售那种"还进去就一直能循环借"的灵活度。

系统里常见的循环机制有四类：不循环一次性额度、借据全部结清后才循环、单一借据结清即循环、还款即恢复循环；对公项目贷款多为不循环，流动资金贷款和零售消费贷多为循环额度，差异由产品配置决定。

把额度、合同、借据三者放在一起看，信贷系统的数据主干就清晰了：额度是"上限"，合同是"约定"，借据是"实际发生的钱"。客户获得额度，额度内签约，合同下放款形成借据，借据还款释放额度。三者通过状态机各自管理生命周期，又通过占用、关联关系彼此联动。理解了这个主干，再回头看贷前贷中贷后的流程，每个环节在数据模型上的位置就一目了然了。

# （五）额度并发扣减的工程实现

图2-34高并发下额度扣减的工程实现流程

额度是高并发热点，前面已经提过，这里给出工程上的标准解法。额度扣减必须满足"先校验、后扣减、扣减即记账"，且整个过程要防止超额支用。最直接的做法是数据库行锁。以一次支用为例，事务内部的执行顺序是这样的：先对额度记录加行锁，把同时操作同一额度的并发请求串行化，在锁内比较剩余可用额度与支用金额，不足就直接拒绝。校验通过后做三件事，原子扣减额度余额、写入一条占用流水、生成支用记录，三者在同一个事务里完成。

用行锁串行化额度操作，虽然牺牲了一点吞吐，但保证了绝对正确。对于超高并发的场景，可以用乐观锁加版本号，扣减时校验版本号，失败就重试。无论哪种方案，额度流水必须记录每一笔占用和释放，这是额度余额可解释的基础。我在做额度系统时的铁律：余额永远靠流水累加，不靠字段反推。

额度占用与释放的时机，还要和借据状态联动。借据放款成功占用额度，借据还款释放额度，借据冲正要回补占用，这些联动在代码里必须和借据状态迁移放在同一个事务里。一个常见的bug 是：借据结清了，额度却没释放，客户明明还清了贷款，可用额度却不涨，投诉和错账接踵而来。所以额度与借据的联动，要做到"借据状态一变，额度必须同步变"，并且要能通过对账发现不一致。

# （六）额度状态机的迁移规则

图2-35额度状态机完整迁移规则

额度状态机的迁移规则，是额度系统设计的核心配置。把额度的主要状态和迁移条件集中成一张表，运营和开发就有了共同语言：

表2-5额度状态机迁移规则

当前状态事件目标状态触发条件
待生效额度开户/审批通过生效授信审批通过
生效支用占用生效（余额减少）支用放款成功
生效风险冻结冻结出现风险信号
冻结风险解除生效冻结原因消除
生效/冻结到期失效超过有效期

这张表隐含了一个容易被忽略的点：额度状态和额度余额是两回事。状态描述"能不能用"，余额描述"能用多少"。冻结是状态迁移，余额不变；支用是余额变动，状态不变（仍可用）。把两者分开，额度系统的设计就清晰了：状态由状态机管理，余额由账务管理，两者通过占用流水联动。很多额度系统的混乱，都源于把状态和余额混在一个字段里。冻结时改余额，支用时改状态，最后既说不清状态也说不清余额。记住这个区分，额度系统的地基就稳了。
